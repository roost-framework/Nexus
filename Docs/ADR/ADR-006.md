# ADR-006: Sprint 3 — Plug Lifecycle Hooks and Two-Phase Plug Configuration

**Status:** Accepted
**Date:** 2026-03-25
**Owner:** Alembic Labs
**Sprint:** 3

---

## Context

The current `Plug` typealias (`@Sendable (Connection) async throws -> Connection`) covers
the core composability story well but lacks two patterns that Elixir's Plug provides and
that real-world middleware pipelines need:

### 1. Lifecycle Hooks (`before_send` / `after_send`)

Elixir Plug offers `register_before_send(conn, callback)` — a mechanism to register
callbacks on a connection that fire just before the response is serialized and sent to
the client. This enables cross-cutting concerns that need to observe or modify the
**final** response without being position-dependent in the pipeline:

- **Response compression** — inspect the final body and apply gzip/deflate.
- **Security headers** — ensure `X-Content-Type-Options`, `Strict-Transport-Security`,
  etc. are always present, regardless of which plug built the response.
- **Logging / metrics** — capture the final status code and response size after all
  plugs have run, including error-formatting plugs.
- **Cookie serialization** — collect cookies set by various plugs and serialize them
  into `Set-Cookie` headers at the end.

Today, achieving this requires careful ordering of plugs in the pipeline, which is
fragile and error-prone. A plug at position N cannot guarantee it will see the final
response shape because a plug at position N+1 may modify it.

### 2. Two-Phase Plug Configuration (`init` / `call`)

Elixir module plugs separate **configuration** (`init/1`, evaluated once at compile
time) from **execution** (`call/2`, evaluated per request). This enables:

- Expensive setup (regex compilation, option validation, key derivation) to happen once.
- Runtime options to be validated eagerly at boot rather than failing on the first
  request.
- A uniform interface for framework-level plug introspection and documentation.

Our current approach — closures that capture configuration — is ergonomic for simple
cases but provides no structured way to validate options upfront or distinguish
configuration errors from runtime errors.

## Decision

### Lifecycle Hooks

Add a `beforeSend` callback array to `Connection`:

```swift
public struct Connection: Sendable {
    // ... existing fields ...

    /// Callbacks invoked in LIFO order just before the response is delivered.
    /// Each callback receives the connection and returns a (possibly modified)
    /// connection. Registered via ``registerBeforeSend(_:)``.
    public var beforeSend: [@Sendable (Connection) -> Connection]
}
```

Registration helper:

```swift
extension Connection {
    /// Registers a callback to be invoked just before the response is sent.
    ///
    /// Callbacks are invoked in reverse registration order (LIFO) — the last
    /// registered callback runs first, mirroring Elixir Plug behaviour.
    ///
    /// - Parameter callback: A function that may inspect or modify the
    ///   connection's response fields.
    /// - Returns: A new connection with the callback registered.
    public func registerBeforeSend(
        _ callback: @escaping @Sendable (Connection) -> Connection
    ) -> Connection
}
```

The server adapter (`NexusHummingbird`) is responsible for draining the `beforeSend`
stack before serializing the response. A `runBeforeSend()` helper on `Connection` will
fold the callbacks in LIFO order and clear the array to prevent double-invocation:

```swift
extension Connection {
    /// Executes all registered ``beforeSend`` callbacks in LIFO order and
    /// returns the resulting connection with the callback list cleared.
    public func runBeforeSend() -> Connection
}
```

### Two-Phase Plug Configuration (`ConfigurablePlug` protocol)

Introduce a protocol for plugs that need structured configuration:

```swift
/// A plug with a distinct configuration phase.
///
/// Conforming types separate one-time option validation (``init(options:)``)
/// from per-request execution (``call(_:)``). The framework calls `init`
/// once at pipeline assembly time and `call` on every request.
public protocol ConfigurablePlug: Sendable {
    /// The type of options this plug accepts.
    associatedtype Options: Sendable

    /// Validates and transforms raw options into the form used at runtime.
    ///
    /// Called once when the pipeline is assembled. Throw here to surface
    /// configuration errors eagerly.
    ///
    /// - Parameter options: The caller-supplied configuration.
    /// - Throws: If the options are invalid.
    init(options: Options) throws

    /// Processes a connection using the pre-validated configuration.
    ///
    /// - Parameter connection: The incoming connection.
    /// - Returns: The transformed connection.
    /// - Throws: Infrastructure errors only (see ADR-004).
    func call(_ connection: Connection) async throws -> Connection
}
```

A bridge to the function-based `Plug` world:

```swift
extension ConfigurablePlug {
    /// Returns a ``Plug`` closure that calls this configurable plug's
    /// ``call(_:)`` method.
    public func asPlug() -> Plug
}
```

This keeps `Plug` as the universal currency type. `ConfigurablePlug` is opt-in for
plugs that benefit from the two-phase pattern. Simple closure-based plugs remain
first-class.

| Deliverable | Target |

| `Connection.beforeSend` field and `registerBeforeSend(_:)` | `Nexus` core |

| Example plugs: `SecurityHeaders`, `RequestLogger` using both patterns | `NexusTests` or examples |

## Consequences

**Positive**
- Lifecycle hooks give plugs a reliable way to observe or modify the final response
  without depending on pipeline ordering.
- `ConfigurablePlug` surfaces configuration errors at assembly time, not at first
  request — fail fast.
- Both features are additive. Existing `Plug` closures and pipelines work unchanged.
- LIFO callback ordering matches Elixir Plug's semantics — familiar to developers
  coming from that ecosystem.

**Negative / Trade-offs**
- `beforeSend` callbacks add a stored array to `Connection`, increasing its size.
  Acceptable: the array is empty by default and only allocated when a plug registers
  a callback.
- `ConfigurablePlug` introduces the first protocol in the plug system (ADR-003 chose
  a typealias). This is intentionally scoped — `ConfigurablePlug` is opt-in and bridges
  back to `Plug` via `asPlug()`. The typealias remains the primary composition unit.
- Server adapters **must** call `runBeforeSend()`. If a custom adapter forgets,
  callbacks silently don't fire. Documented prominently and enforced via adapter tests.
