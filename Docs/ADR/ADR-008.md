# ADR-008: Response producers follow transport demand

**Status:** Accepted
**Date:** 2026-10-04

## Context

The chunked, file, and SSE helpers created unbounded continuation streams and
unstructured tasks. Awaiting writes in an adapter could not slow those upstream
producers. Dropping a response or failing a transport write did not reliably
stop the tasks. SSE also introduced a second buffering bridge.

## Decision

Extend ADR-002 with a fourth response body case:

```swift
case producer(@Sendable (inout any ResponseBodyWriter) async throws -> Void)
```

`ResponseBodyWriter.write(Data)` is async and throwing. String and SSE helpers
encode into this method. The writer stays in the response task; it is not a
Sendable handle for launching independent producers. Every write must be awaited.

Both adapters invoke the producer within the native response body callback and
await their transport writer. Nexus adds neither a queue nor a producer task.
Returning finishes the native body; throwing aborts delivery. Each write checks
task cancellation before and after the transport operation. Suppressed response
bodies never start the producer. Once headers are sent, an error aborts the
stream; it cannot replace the status with a new HTTP response.

`sendChunked`, `sendFile`, and `Connection.sseEvent` use this path. Files open
inside the producer, close with `defer`, and read one chunk per completed write.
SSE sets its headers and halts like other terminal response helpers.

## Compatibility

This is a source-breaking helper change: add `try await` to writes, return instead
of calling `finish`, throw instead of `finish(throwing:)`, and replace SSE
continuations/nested tasks with direct writer calls. Exhaustive response switches
must handle `.producer`. Raw `.stream(AsyncThrowingStream)` remains available;
its buffering and producer cancellation remain the caller's responsibility.

File existence/readability is checked while preparing the response, but opening
is deferred. Filesystem changes between those stages can cause a stream failure.

## Boundaries

- Transport acceptance is not client acknowledgement. NIO and the OS still buffer.
- Disconnects reach these producers through failed writes. An idle producer
  waiting on unrelated work is not guaranteed immediate cancellation; SSE callers
  should send periodic heartbeat comments and propagate errors. Vapor's public
  middleware interface does not expose a channel-close callback.
- Cancellation is cooperative. CPU loops and swallowed write errors are outside
  the guarantee. A producer must not retain the writer or launch detached work.
- FileHandle reads remain synchronous per chunk. Moving filesystem I/O to an
  executor or native file region is a separate performance change.
- This pilot covers HTTP/1 over local TCP, not HTTP/2, TLS, proxies, or throughput.
  Streamed uploads and compression are outside its scope.

## Validation

Core tests verify lazy startup, cancellation/error cleanup, SSE encoding, and
file read pacing by truncating the unread tail while a write is suspended.
The same live TCP suite runs against both adapters: exact 2 MiB file delivery to
a slow reader, SSE framing/automatic completion, aborted producer errors, and
suppressed-body laziness. Stalled-reader probes use a sparse 256 MiB file and a
comparable SSE source, bound the client's buffers, require production below
32 MiB, then disconnect and require producer cleanup within five seconds.
This demonstrates pacing and cleanup; it is not an RSS or load benchmark.

On 2026-10-04, all 967 tests passed on macOS (Swift 6.4) and Linux arm64
(the CI `swift:6.0` image). Both runs include two intentional known-issue probes
for the SwiftCheck assertion bridge. Focused formatting and `git diff --check`
also passed. Linux validation required explicit byte-view conversions in two
Hummingbird tests and splitting an optional-chain assertion for Swift Testing 6.0.
